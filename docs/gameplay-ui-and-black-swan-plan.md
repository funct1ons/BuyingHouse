# 游玩体验改进方案：界面简化、快报消歧与黑天鹅事件

> 状态：**待确认的修改方案，尚未实施**。本次只新增本文档，不修改游戏代码、测试代码、存档或历史验收报告。
>
> 调研日期：2026-10-04。工作区基线：`a538345`（`feat: deepen market rotation and save migration`）。真实新闻参考范围按最新建议扩大为 **2016-10-04 至 2026-10-04**；优先选取机制清楚、能映射到现有商品的原型，不要求每个年份都有事件。

## 1. 需求与总体结论

本方案覆盖两次补充后的六项需求：

| 编号 | 游玩建议 | 推荐改法 | 实施性质 |
|---|---|---|---|
| U1 | 商品少，有分类，搜索框无意义 | 完全删除搜索；保留分类、关注、持仓查看和排序 | 展示与交互 |
| U2 | 出售需要找持仓，再进详情，操作繁琐 | 合并仓储与持仓，逐商品提供直接出售按钮和内联自定义数量 | 展示与交互，不改成交规则 |
| U3 | 街区快报比城市来信重要，应交换位置 | 快报移到右侧完整决策栏；来信移到市场上方的紧凑区域 | 展示与信息分组 |
| U4 | 下一周频繁使用，应在底部中央且更显眼 | 底部三段式布局，主按钮真正水平居中，独立于保存按钮 | 展示与交互 |
| U5 | 轮换行的百分比不知对应哪个商品 | 到货／缺货行不再挂一个总百分比；其他百分比必须紧邻商品名 | 信息语义 |
| G1 | 行情过于平稳，增加较常见的黑天鹅事件 | 单独设置重大冲击事件池、触发概率、冷却和年度上限；用近十年新闻作为创作原型 | **经济规则变更，另行冻结与验证** |

**分两阶段实施，不将 UI 调整与经济调参混成一个无法定位问题的大改动。**

- **阶段 A：界面与快报消歧。** 完成 U1–U5，不改变经济规则、随机序列或存档格式。
- **阶段 B：黑天鹅玩法。** 确认事件目录、概率、数值、版本与迁移方案之后，才修改引擎，并重新做平衡验证。
- 本文中的尺寸、概率、事件幅度和诊断目标是**推荐初值，不是已测结果，也不是自动获批的冻结参数**。

## 2. 已阅读的工作区与现状

### 2.1 项目边界

游戏《这一年，安个家》是本地运行的 HTML／CSS／原生 JavaScript 游戏。玩家直接打开 `index.html`，不需要安装 npm 包、启动服务或联网。目标是在 52 周中经营商品并实际购置住房。

当前生产代码的经济规则为 `0.4`、存档版本为 `3`，价格簿为 `0.2`。视听发布标签不等于经济版本。保留商品池有 12 种，每周 8 种在售；另有 8 种旧档退出商品，只能回收出售。

调研依据包括：

- `README.md`、`docs/design.md`、`docs/ui.md`：项目结构、早期设计和界面约定。
- `docs/gameplay-handoff.md`、`docs/gameplay-rule-freeze.md`、`docs/gameplay-release-review.md`：现行规则、禁止擅改的事项、模拟证据和未验边界。
- `js/ui.js`、`css/main.css`、`css/scenes.css`、`index.html`：真实界面、事件绑定和样式覆盖。
- `js/data.js`、`js/market.js`、`js/math.js`、`js/trading.js`、`js/game.js`、`js/save.js`、`js/validation.js`：商品、事件、交易、随机性、存档和严格校验。
- `tests/ui-interaction.cjs`、`tests/milestone-b-edge*.cjs`、`tests/milestone-d-edge.cjs`、`tests/av-visual.cjs` 等：需要适配的旧断言。
- `simulation/c1.cjs`：现行六策略、三难度和主／留出样本计量方法。

历史设计文档存在旧版本内容，实施时以**当前生产源码与交接文档**为准。已有 `docs/gameplay-evidence/week2-bulletin-1366.png` 和 `week2-bulletin-1600.png` 用于观察现状，**不是本次重新运行浏览器获得的证据**。

### 2.2 当前布局与操作问题

当前主界面：

```text
顶部：周数、现金、净资产、容量、帮助／设置／主页

左侧                      中间                         右侧
住房与买房目标             街区快报（最多三条）          城市来信（大块区域）
我的仓储：容量／升级        市场标题                     持续市场消息＋生活事件
                          搜索＋查看范围＋排序          手里的货（高度受限）
                          分类＋商品卡片

底部左侧：保存状态、快捷键                     底部右侧：保存、下一周
```

具体原因：

1. 搜索不仅占空间，还能把默认 8 件在售商品扩展为更大的目录，增加了“本周可买”和“仅能卖出”的理解成本。
2. 左侧“我的仓储”只有空间信息；右侧“手里的货”只是打开售卖弹窗的入口。容量与可卖库存分离，出售仍需要多步操作。
3. 快报直接挤占市场高度；来信即使只有空状态也占据大片空间。1366×768 的历史截图中，市场首屏能完整看到的商品行数偏少。
4. `footer` 采用左右分布，下一周与保存并排靠右，不符合最频繁操作的视觉重心。
5. 轮换新闻的 `productId` 实际只绑定一个代表商品：有新到货时取排序后的第一件到货商品，否则取第一件缺货商品。通用快报渲染却把它的 `changeBps` 挂在整句“新到货／暂时缺货”后，容易误读成所有商品或全市场的涨跌。
6. “城市来信”并非全是低价值信息：其中还包含 `ongoing` 持续市场事件。直接整体降权会隐藏有效决策信息。

### 2.3 当前已有强冲击，但没有独立黑天鹅层级

不能把现状描述成“完全没有大事件”。当前已有：

- 每次推进周，普通市场事件的抽取门槛概率为 `0.42`，个人现金事件为 `0.08`；同周最多新抽取一个市场事件。普通事件选中已生效 id 时会跳过，因此实际新增率不一定等于 42%。
- `immediate` 一次性冲击、`persist` 持续中枢变化、`structural` 结构性中枢变化。
- 例如芯片事件显卡首冲 `+7000 bps`、藏品活动 `+9000 bps`、热度消退 `-5000 bps`、防护需求 `+8000 bps`。
- 当前新闻已在价格变化后生成，百分比来自真实当周行情，而不是直接抄事件配置。

因此 G1 应解决的是：**重大事件辨识度、事件原型多样性、有效出现频率和具体冲击的可见性**，而不是简单把所有普通噪声翻倍。

既有模拟还显示标准难度多种策略购房率偏低，价值策略明显更强。不能因为要“更刺激”就认定当前经济已经平衡，也不能擅自降房价作为补偿。

### 3.2 布局约束

- 左侧建议约 270–300 CSS px，右侧约 300–340 CSS px；中间优先获得剩余宽度。以 1366×768 和 1280×720 的实际可用空间校准，而不是只在大屏上设计。
- 左侧住房区减少装饰性留白和重复抒情文案，插画与买房目标仍保留；合并仓库占据左侧剩余高度。
- 仓库头部、快报标题、市场工具栏不随各自列表滚走；分别使用内部滚动容器，避免整页和多个嵌套列表抢滚动。
- 城市来信默认是紧凑摘要。展开详细内容后允许内部滚动，建议不超过中央工作区约四分之一高度；不采用无上限撑开的长卡片。
- 在标准新局、无迁移提示、来信未展开的 1366×768 基准场景，目标是首屏**完整展示至少两行、共四张市场卡片**。这是待实施验证的目标，不是现有通过结果。
- 保留暖纸色、青绿主操作、陶红上涨／绿色下跌、本地 SVG 与住房插画，不重做美术和音乐。
- `css/scenes.css` 在 `css/main.css` 后加载，两者必须一并核查，尤其是 `.market-panel`、`.letter`、`.ledger` 和 `.inventory-line` 的覆盖。

支持视口：1366×768、1600×900、1920×1080、2560×1440，以及 1920×1080 的 125%／150% 等效视口 1536×864、1280×720。

小于约 1100 CSS px 时采用降级布局：左侧仓库，右侧快报在市场上方；更窄时单列、快报优先，并允许纵向页面滚动。底部操作栏仍保留居中入口。该降级只保证可操作，不把本轮扩大为完整移动端重设计。

## 4. U1：删除搜索，不破坏商品访问路径

### 4.1 展示变化

- 删除搜索输入框、占位文案、搜索状态和专属监听，不只是用 CSS 隐藏。
- 保留“全部商品／我的持仓／我的关注”、现有分类和五种排序。
- “我的持仓”仍可用于跨商品行情比较；直接出售的主要入口改为左侧仓库，不强迫玩家先切换该筛选。
- 默认视图继续显示本周在售商品。显示范围与排序保持现有跨周行为，推进周后仍切到“本周关注”排序；本轮不顺手重写筛选规则。
- 工具栏可显示“本周在售 8 种／当前显示 N 种”。在持仓或关注视图中，N 不必等于 8，应明确区分。
- 分类／关注筛选为空时，提供“查看全部商品”的重置入口，而不是提示玩家搜索。

### 4.2 必须保留的边界

- 未上架的保留商品，只要有持仓，必须仍能在合并仓库中看到并出售。
- 8 种退出商品的旧档持仓也必须保留，不能随着搜索分支删除而失去入口。
- 数字键 `1–9` 仍按**当前市场列表的实际顺序**打开商品，不按全目录索引。只有 8 张卡片时，按 `9` 不应打开隐藏商品。
- 关注、筛选、排序和查看详情不推进周、不改变随机流、不生成交易。
- 帮助、首次引导、`README.md`、`docs/ui.md` 和依赖搜索的测试需要在实施时同步更新；本次不提前改这些文件。

## 5. U2：合并仓库，直接出售

### 5.1 仓库信息层级

合并模块分为固定摘要和可滚动持仓：

1. **固定摘要：** 仓储等级、已占／总容量、剩余空间、升级按钮。
2. **持仓列表：** 展示全部数量大于零的保留商品与退出商品，不受市场分类、关注和排序影响。
3. **空状态：** “仓库还没有货，去街区市场看看。”不显示可点击的出售按钮。

每个持仓卡片应包含：

- 商品名、持有数量、占用空间。
- 明确渠道标记：`本周在售`、`未上架 · 回收折价 8%`、`已退出 · 冻结参考价回收`。
- 当前成交／回收单价、全部持仓预计净回款，以及按当前渠道计算的未实现盈亏。
- 三个主按钮：**卖 1、卖 5、卖全部**。
- 次级入口：**自定义数量、查看详情**。

“卖全部”始终只指**当前这一种商品**，本轮不增加全仓一键清空。

### 5.2 直接出售的交互规则

| 操作 | 推荐行为 |
|---|---|
| 卖 1 | 立即提交一次卖出 1 件的交易 |
| 卖 5 | 立即提交一次卖出 5 件的交易；不足 5 件时禁用，不偷偷改成卖剩余数量 |
| 卖全部 | 按提交时的最新持仓数量，一次卖光该商品 |
| 自定义数量 | 当前卡片内展开数量输入、预览和“确认卖出”，不必进入商品详情弹窗 |
| 查看详情 | 保留原商品曲线、说明、买卖弹窗，作为可选的深入查看路径 |

推荐普通快捷出售**不再弹第二个确认框**，包括亏损卖出和回收出售。保护措施放在持续可见的渠道、净回款提示、清楚的按钮命名和重复提交防护上，不把旧流程重新套回去。

数量输入保持现有正整数校验：不能含小数、负号或科学计数法，不能超过持仓和当前 UI 的有效数量上限。切周、导入或持仓变化后，必须重算预览；无效时禁用确认按钮并给出原因，不能沿用旧价格提交。

### 5.3 金额口径：必须复用真实交易规则

所有金额内部以整数“分”计算，调用现有 `H.channelUnit`、`H.channelGross`、`H.channelNet`、`H.fee` 和持仓成本函数。不能另写一套近似报价。

```text
本周在售：成交单价 = 当周市价
未上架／退出：回收单价 = 现有 buybackQuote（按单价先取整）
成交额 = 成交单价 × 本次数量
手续费 = 对本次整笔成交额，按现有规则向上取整
净回款 = 成交额 − 手续费
全部持仓盈亏 = 全部预计净回款 − 当前持仓成本
```

- 不能用“参考市值 × 0.99”替代回收净额，也不能把“单件净回款 × 5”当作卖 5 件的预览。
- 一次卖 5 件与分五次卖 1 件的手续费可能不同，要保持真实账本，不抹平差异。
- 部分卖出的成本分摊、清仓余数、`stats`、`byProduct` 和容量释放全部继续由交易引擎处理。
- 整个仓库摘要中的“可变现净额”使用 `H.liquidValue`，不得与顶部账面净资产混为一谈。
- 默认持续显示“卖全部”净额；聚焦快捷数量按钮或展开自定义数量时，内联显示对应数量的净额与手续费。关键金额不能只藏在鼠标悬停提示里。

### 5.4 提交、反馈和焦点

- 新快捷按钮必须复用 `act()`，或与原弹窗共用同一 UI 提交封装，再调用 `Engine.dispatch`。禁止直接改 `inventory`、`cash` 或直接调用 `H.trade` 绕过引擎。
- 保留 `revision`、唯一 `token`、状态校验、保存回调、交易音效和错误提示。
- 提交期间立即锁定对应操作。现有 220 ms 防抖不足以覆盖全部重复操作：需要同时处理原生双击的第二次点击和键盘长按；一次手势只成交一次，之后正常独立点击仍可继续交易。
- 成功提示应具体，例如“已卖出手机 × 5，净回款 ¥…”，同时更新现金、数量、剩余空间和盈亏。
- 自动保存失败时，明确区分“交易已成功，但未保存”，不能重试交易来解决保存问题；自动保存关闭时继续提示进度未必已保存。
- `renderGame()` 当前会整体替换 DOM。更新前记录仓库列表滚动位置和**逻辑焦点**，更新后定位到同商品的相应按钮。
- 清仓导致卡片消失时，焦点移到下一张持仓卡、上一张或仓库标题，不能意外跳到“下一周”。
- 内联展开状态、草稿数量、焦点与滚动位置属于 UI 临时状态，不写入游戏存档；换局／导入时清理，切周后校验或清理旧草稿。
- 卡片外层使用 `article`／`div`，不能把带多个出售按钮的卡片整体包在另一个 `button` 内。

## 6. U3：街区快报与城市来信重新分工

### 6.1 右侧完整决策栏

右侧“街区快报”按以下顺序组织：

1. 固定标题、当前周、现有市场景气标签。
2. 本周头条：具体情境、明确绑定商品的实际涨跌、可买／仅可回收状态、关联持仓与详情入口。
3. 持仓异动或其他重点异动。
4. 新到货／暂时缺货：轮换事实，不附一个无主语的百分比。
5. **仍在影响：** 从原来信区移入 `ongoing` 持续市场消息，明确不是新的冲击。

保留 `H.bulletinRows(s.news)` 的现有三条主摘要选择，不为了填满右栏而编造更多头条。“仍在影响”是额外展示分组，**不是新增 `s.news` 条目，也不突破引擎三条快报摘要的校验**。

持续事件只表示已有影响尚未结束，不能宣传下周必然同向。无新事件但已有明显价格异动时，继续使用现有 `move` 情境，不伪造新闻原因。

### 6.2 中央紧凑来信

- 城市来信仅保留 `personal` 生活现金事件，明确“仅影响现金，不改变商品行情”。
- 市场景气和 `ongoing` 不再重复出现在来信里。
- 无生活事件时是一行安静状态，不再使用“没有持续市场消息”作为城市来信的空文案。
- 有生活事件时默认摘要显示事件标题，并可展示已结算的现金影响；展开看详情，不阻断操作。
- 保持原事件生成和结算：改变的是 UI 分组，不更改 `s.news`、个人事件概率或现金处理顺序。

这会替代 `docs/gameplay-rule-freeze.md` 第 6.1 节旧的**布局位置约定**，但不更改其中的经济时序、头条选择、可靠性、真实涨跌和不预测未来等约束。批准实施后，应补写变更记录，而不是把历史冻结文档静默改成“原来就如此”。

## 7. U5：消除轮换百分比歧义

### 7.1 推荐：轮换行不显示总百分比

当前容易误读的样式：

```text
新到货：雨具；暂时缺货：猪肉  +3.6%
```

推荐改成：

```text
货架轮换
新到货：雨具；暂时缺货：猪肉
雨具 · 本周可买                         [查看雨具]
```

以上仅为样式示例，商品名和状态来自当前新闻／行情，不能硬编码。

- 到货／缺货表达的是**上架状态变化**，不是价格变化，不在整句尾部显示百分比。
- 如保留该行代表商品的持仓、净额或查看按钮，必须加商品名，避免百分比虽然删了、其他数字仍然无主语。
- 本轮不改变引擎“选取代表到货／缺货商品”的规则，也不解析中文标题去反推商品 id。
- 未上架商品的直接售卖入口在合并仓库中，不要求轮换行一定提供所有商品的交易按钮。

### 7.2 所有行情百分比的统一规范

其他行也采用独立的、明确绑定商品的行情标签：

```text
显卡 · 本周 -42.0%
```

- 每个百分比都紧邻商品名，辅助说明为“相对上周成交价”。
- 只能来自该商品当前真实 `price`／`previous`，沿用 `H.changeBps`，显示层再格式化。
- 多商品事件不能把最显著商品的涨跌误称为“全市场涨跌”。
- 新到货商品的周涨跌比较对象是**上一个自然周**，不是上一次在售的那一周。
- 事件配置的冲击 bps 是引擎输入，实际周涨跌还受噪声、其他有效中枢和价格边界影响，二者不可互换。

## 8. U4：底部中央的周推进按钮

### 8.1 视觉与位置

底栏采用三段式 CSS Grid：左、右区域等宽，中间放主按钮。可使用 `minmax(0, 1fr) auto minmax(0, 1fr)`，而不是把“保存＋下一周”整体居中；否则下一周按钮本身仍然偏离中心。

- 主按钮建议宽 220–280 CSS px、高至少 48 CSS px，青绿色实底、较强文字对比、适度边框／阴影。
- 使用“进入下一周 →”，可附次级说明“第 N 周 → 第 N+1 周”；不使用持续闪烁或大型警报动画。
- 保存状态和快捷键放左侧，手动保存放右侧，用次级按钮样式。
- 桌面支持视口中，主按钮保持完全可见，中心与视口水平中心偏差目标不超过 4 CSS px，不受左右文本长度影响。
- 在较低高度下，底栏建议预留约 64 CSS px，避免按钮被现有 48 px 短底栏挤压；工作区使用 `min-height: 0` 正确分配剩余高度。
- Toast 不能遮挡主按钮或仓库出售按钮。

### 8.2 行为不变，但完善键盘冲突

- 第 1–51 周推进到下一周；第 52 周改为“结束本年”，仍须结束确认；已结束时为“查看年度结算”。没有第 53 周。
- 保留 `data-testid="next-week"`；已结束时继续使用结果动作，而不是错误地调用 `next`。
- 保留空格推进，但只在没有弹窗、没有编辑输入、没有局部交互控件接管空格时触发。
- 当焦点在出售／保存／展开等原生按钮时，空格和 Enter 只激活该按钮，不同时触发周推进。不要让全局空格快捷键截获原生按钮。
- 数量输入、选择框、文本编辑和弹窗内空格均不推进；按住空格／Enter 不连续推进或连续卖货。
- 新周行情和音效只在本次成功 `next` 后发生一次；刷新、继续、导入、展开来信和卖货不重播新周提示。

## 9. 阶段 B：黑天鹅事件的设计目标

这里的“黑天鹅”采用**游戏化的重大突发冲击**含义，不严格限定为现实金融理论中无法预见的事件。某些现实事件（例如计划中的协议升级、渐进的气候风险）不属于严格意义上的黑天鹅，只适合作为素材备选，不能混淆概念。

目标是：每局有少量值得记住的突发转折，能让不同商品出现明显机会和风险，玩家能看懂“什么发生了、哪些商品受影响、现在能做什么”。

不做：

- 每周全市场暴涨暴跌，或把普通随机噪声整体翻倍。
- 根据玩家现金、持仓、已实现利润或即将买房的进度定向打击／送收益。
- 保证新闻后继续上涨、规定几周后必然反弹、提供未来方向传闻。
- 自动清空库存、损毁住房、强制借贷，或用灾难新闻直接扣大笔现金。
- 照搬现实品牌、国家冲突、伤亡叙事或新闻正文；游戏事件使用虚构城市和原创文案。
- 为新事件重新引入黄金、能源、药品等已退出商品。第一版仅作用于现有 12 种保留商品，8 种退出商品继续冻结参考价。

## 11. 推荐第一版事件目录

下面七个事件是**虚构城市的原创设计**。百分比是待调试的首冲配置，不是新闻来源中的实测价格，也不是最终 UI 的涨跌展示值。`100 bps = 1%`。

| 候选 id／标题 | 原型 | 首周效果（配置值） | 机制／持续周数 | 原创情境与决策取舍 |
|---|---|---|---|---|
| `swan_route` 主航道临时封航，进口柜台等不到货 | S2 | 手机 `+4000`、显卡 `+3000`、空调 `+2500 bps` | 各商品 `persist`，3 周 | 在途货物延迟，街区进口耐用品供给收紧；已经持货者可兑现，追入者承担供给恢复风险 |
| `swan_efficiency` 新算法落地，旧算力订单突然撤回 | S4 | 显卡 `-5000`、手机 `-1500 bps` | `immediate`，1 周 | 虚构的技术效率突破使部分旧硬件订单被撤回；手机影响是本游戏额外设定，不冒充现实新闻结论 |
| `swan_egg_short` 多地蛋场临时停供，批发柜台告急 | S5 | 鸡蛋 `+5500`、大米 `+1000 bps` | `immediate`，1 周 | 供给骤紧；大米的替代需求是游戏设定。余波由已改变的价格和正常回归形成，不逐周重复冲击 |
| `swan_heat` 异常热浪提前压城，制冷货源吃紧 | S7 | 空调 `+5000`、水果 `+3000`、雨具 `-1500 bps` | 各商品 `persist`，3 周 | 制冷需求和农产品供给压力并存；雨具转弱是虚构的热旱背景，不是高温必然导致的现实结果 |
| `swan_tariff` 进口新规突然生效，柜台成本与消费预期分化 | S6 | 手机 `+3500`、名表 `-2500`、城市藏品 `-4000 bps` | 各商品 `persist`，2 周 | 手机成本上升，可选消费需求转弱；同一事件有涨有跌，不用一个“全市场百分比”概括 |
| `swan_protection` 防护标准临时升级，常备用品突然紧俏 | S1 | 口罩 `+11000`、大米 `+2000`、鸡蛋 `+1500 bps` | `immediate`，1 周 | 临时防护及常备需求挤压现有供给；不强调恐慌、不把真实健康危机包装成发财教程 |
| `swan_egg_relief` 加急蛋品到货，短缺预期迅速消退 | S5 | 鸡蛋 `-4500`、大米 `-1000 bps` | `immediate`，1 周 | 需求降温与到货缓解预期；不是 `swan_egg_short` 的定时后续，不保证先涨再跌的配对链 |

说明：

- 直接影响 1–3 种商品，覆盖日常、产业、投机与应急，而不是全靠显卡／名表制造刺激。
- 目录另定义 `primaryProducts`，用于候选可见性过滤与主冲击诊断：航道事件为手机，算法事件为显卡，两个蛋品事件为鸡蛋，热浪事件为空调，进口新规为手机／城市藏品，防护事件为口罩。它与新闻最终选出的最大实际异动商品不是同一个概念。
- 同一商品每个事件只使用一种效果类型。`persist` 首周冲一次，随后只改变中枢；`immediate` 到下一周不再另加同百分比。
- `swan_heat` 候选仅在游戏夏季可抽取；其他候选无现实日历绑定。
- 七个事件暂按相同权重选取，不引入另一套未经定义的权重算法。运行诊断后才提出更改权重。
- 已有普通事件保留原幅度，黑天鹅是独立的事件层级。普通抽奖池必须显式排除黑天鹅目录，不能把黑天鹅加入 `type: 'market'` 后又被原 42% 抽奖选中，绕过冷却和年度上限。新标题不能仅替换旧事件名称，却让两套同主题事件并行叠加。
- 角色持续中枢护栏仍是日常 ±3000、产业 ±6000、投机 ±8000；本表的大米等持续值不超过对应护栏。一次性鸡蛋 `+5500` 不作为日常持续中枢值保存。
- 保留所有商品现有价格上下界、1% 买卖手续费、8% 回收折价、住房／仓储 `0.2` 价格簿。价格边界可能让真实冲击小于配置，必须诊断，不能为了显得刺激自动放宽上限。
- Ethereum 挖矿用途变化和大停电先做备用，不首发：前者与显卡下跌原型重复且可预告，后者与保留商品的直接映射较弱。

## 12. 触发频率、冷却与公平性

### 12.1 推荐初值

| 参数 | 推荐初值 | 理由 |
|---|---|---|
| 可触发周 | 第 4–50 周 | 开局留出学习空间，最后两周不新增重大冲击；已生效影响正常延续 |
| 黑天鹅触发概率 | **16%，仅在符合条件的周判定** | 比现实高；不是在原 42% 事件概率上再乘 16% |
| 冷却 | 触发后完整 5 周不再新增黑天鹅 | 两次黑天鹅起始周至少相差 6，保留消化行情的时间 |
| 年度上限 | 最多 6 次 | 防止连续刺激取代经营决策 |
| 同一事件 | 同一局最多一次 | 避免固定灾难反复刷收益／刷亏损 |
| 同周新市场事件 | 最多 1 个 | 黑天鹅成功触发时替代当周普通新市场事件，不再加抽普通事件 |
| 未触发黑天鹅时 | 普通事件仍按 42% 判定 | 保留既有普通事件和平静周 |
| 个人事件 | 仍为 8% | 不借黑天鹅改变生活收支规则 |
| 难度 | 同一概率、冷却、目录幅度 | 不给挑战难度叠加一层未说明的事件伤害倍率 |

忽略候选过滤和年度上限的近似平均频率为 `0.16 / (1 + 5 × 0.16)`，47 个可能触发周约 4.2 次。**这只是估算，不是保证每局四次，也不是实测**；候选过滤、季节和已有事件会改变实际次数。推荐用模拟检验“平均约 3–5 次／局”的体验目标。

在符合条件且有候选的周，尝试新增市场事件的理论门槛概率约为 `0.16 + 0.84 × 0.42 = 51.28%`；冷却等不符合条件的周仍走普通事件的 42% 门槛。重复 id、普通候选为空等会使实际新增率更低。统计报告必须分别给出条件触发率、全年度次数、抽取尝试率和实际新增率，不能只写一个“16%”误导。

### 12.2 候选过滤与重叠

先构造候选，再抽取：

1. 当前周、冷却、年度次数满足条件。
2. 本局未发生过该 id，季节要求符合。
3. 至少一个主冲击商品本周在售，保证玩家确实能在当前市场中感知；这不等于保证盈利。
4. 与正在生效的、同主冲击商品的普通短期事件冲突时，暂不作为候选。已经生效的结构性中枢不删除、不逆转，但应在诊断中单列。
5. 黑天鹅 `persist` 仍生效期间，普通新事件不得再命中其受影响商品；可以选择不重叠的普通候选，候选为空就保持平静，不无限重抽。

候选过滤只读周数、季节、上架状态、既有事件和黑天鹅发生记录，**不读玩家现金、数量、盈亏或买房进度**。不得为了避免裁剪而根据当前价格挑一个对玩家更有利的事件。

黑天鹅成功后不抹除已有有效事件，不重设价格、不改宏观状态。过滤、抽取顺序和随机调用次数需要冻结，以保证同版本复现。

### 12.3 时间顺序与随机边界

沿用当前 `next` 的经济时序：

```text
进入新周 → 环境 → 商品轮换 → 清理到期事件／分层抽事件
       → 趋势 → 价格首冲或回归 → 生活现金结算 → 生成真实新闻
       → 记录／校验／提交／保存 → 展示
```

- 第 1 周不开局抽黑天鹅；它只发生在一次成功推进周中。
- 首版继续使用已有 `events` 随机流，不用 `Math.random`、墙钟时间、联网新闻或渲染次数。
- 明确冻结“候选构造 → 合格时抽黑天鹅门槛 → 命中时选候选，否则普通事件 → 个人事件”的调用顺序。
- 与 0.4 相比，未来随机轨迹会改变；只承诺**新版本同种子、同操作可复现**，不承诺跨规则版未来一致。
- 打开快报、出售、筛选、调整音量和读档都不抽事件。恢复存档后，下一次推进与未中断路径一致。
- 到期只停止对应持续中枢影响，不生成镜像反向事件，也不承诺价格回到某一个精确值。

## 13. 黑天鹅在界面中的表达

复用阶段 A 的右侧快报和原商品详情，不增加每次都必须关闭的事件弹窗。

- 快报头条增加“重大事件”标记、清晰情境和事件已发生的说明；强度标记属于事件目录元信息，不伪装成可靠性预测。
- 首条明确显示代表商品名与实际涨跌；下方可列出另外受影响商品各自的**实际当周变化**，最多三件，不使用配置值替代。
- 同时显示该商品是否在售、玩家持仓量和当前渠道；卖出仍走左侧快捷按钮，详情用于进一步查看。
- 本周新冲击与“仍在影响”分开；持续期间不要每周重复“重大事件刚刚发生”。
- 同事件可能导致商品涨跌不同，不用整条新闻的一个百分比概括。
- 多个效应、普通噪声和裁剪会共同影响实际涨跌。措辞使用“本周已发生／当前价格变化”，不把全部波动都归因于该事件。
- 标题和情境不嵌入固定百分比，不出现“必涨／稳赚／抄底”等指令。
- 沿用 `fresh` 头条和现有大异动表现的约束：只在成功 `next` 后短暂强调一次，尊重减少动效、游戏动画设置、静音和页面可见性，不新建重复音乐循环。
- 现有三条摘要结构可以保留：重大事件占头条，异动占第二条，轮换占第三条；多商品行情在头条内部展开，第一版不新增更多新闻 `kind`。

## 14. 版本与存档：阶段 B 必须单独批准

阶段 A 不升规则／存档版本。阶段 B 增加长期冷却与去重记录，不能假装是只加几个标题。

推荐候选：经济规则 `0.5`、存档版本 `4`、主键 `homeyear.save.v4`。最终编号需在实现前确认。

### 14.1 新增状态的最小方案

- 顶层新增 `swanLog: [{id, week}, ...]`，只记录已经成功发生的黑天鹅，不保存未来结果。
- 从该记录派生次数、最后发生周和已使用 id，不再存三份可能互相矛盾的缓存字段。
- 严格校验 id 属于黑天鹅目录、周数在 4–50、顺序递增、相邻至少差 6、无重复 id、最多 6 条、记录周不得晚于当前周；夏季限定事件还需检查发生周的季节。
- 当前有效黑天鹅必须能在日志中找到一致的 id／起始周；黑天鹅头条与持续新闻也要交叉校验，不能靠漏填日志绕过冷却和去重。过期事件的日志则保留，不要求它仍在 `activeEvents` 内。
- 当前 `activeEvents` 仍使用 `{id, started, until}`，新闻仍使用现有八个字段和五种 `kind`。目录可以增加层级／主冲击商品等元信息，保存记录不随意扩字段。
- 新游戏 `swanLog = []`。继续／导入必须带完整记录，不能每次加载清空冷却。

### 14.2 v3 的迁移保护

新建独立、冻结的 v3 校验上下文（候选文件 `js/v3-baseline.js`），不能先把 `version` 改成 4，再交给新校验“蒙混过关”。

对合法 v3：

1. 识别为**旧规则合法存档**，不是“损坏存档”，提供导出和明确迁移选择，不静默升级。
2. 玩家确认之后才备份原文、转换和写入 v4；备份与写入回读必须校验，取消不改旧键。
3. 保留现金、持仓数量和成本、12 品行情、8 品退出商品冻结价、周数、住房、仓储、历史、统计、结果和价格簿。
4. 普通事件目录不改，因此合法正在生效的普通事件可保留；不补抽本周黑天鹅，不重放价格冲击。原新闻保留真实已发生事实。
5. 四条已有随机流保留当前整数；新增 `swanLog = []`，只从迁移后的下一次成功推进周开始进入新调度。
6. 原有 v2→v3 的 `migration` 与原备份引用继续保留，尤其不能丢掉影响旧持仓统计边界的迁移标记。
7. 推荐顶层独立 `upgrade` 字段：原生新局为 `null`，真实 v3 转入时为 `{fromVersion: 3, fromRules: '0.4', atWeek, backup}`。它不能覆盖上述 v2 来源记录。v2 直接转入 v4 时保留原 `migration`、`upgrade = null`，不虚构一次来自本地 v3 原档的迁移。其精确键、备份引用和周数规则一并冻结。
8. 已结束 v3 若转换为 v4，必须仍是 `ended`，结算不变，不能重新开放交易；该路径要独立验收。

v2 的既有保护也保留：原键永不被导入／迁移覆盖；完整独立旧规则校验；已结束 v2 仍按现有边界不迁为可继续局。合法进行中 v2 可以在内存中完成原冻结转换后进入 v4，但不能为了中转写回或覆盖本地 v3 原档。

v4 已存在却损坏时仍隔离，不自动回退旧档覆盖。未知／未来版本只拒绝并保留原文。设置、关注与音量无需因经济版本变化而清空。

### 14.3 必须保持的承诺

迁移提示应明确：“本周已有账目与行情保留；迁移后未来采用新事件规则，同一种子不会沿旧规则继续。”不能承诺旧版未来轨迹一致。

本阶段不放宽资金／成本／手续费恒等式，不删历史来通过校验，不修改 `0.2` 已发布价格簿，也不把未批准的黑天鹅写入已有 v3 目录而不升版。

## 17. 阶段 B 验收与平衡诊断

### 17.1 自动化规则测试

建议新增 `tests/black-swan.cjs` 和 `tests/black-swan-browser.cjs`：

- 第 1–3、51–52 周不能新抽黑天鹅；第 4、50 周边界正确；末周既有持续事件不被错误清除。
- 同周最多一个新市场事件；冷却严格满 5 周；年度不超过 6；同 id 不重复；黑天鹅绝不从普通事件池被抽中绕过限制。
- 季节／上架／重叠过滤正确；没有候选不会无限重抽，也不误记已发生。
- 任一事件只在 `started` 那一周施加首冲；`persist` 后续只改变中枢，`immediate` 不重复复利；到期不生成必然反弹。
- 配置目录只引用 12 个保留商品；退出商品不受冲击；价格仍在既有上下界，金额和账本恒等式保持严格。
- 实际新闻百分比与行情一致；多商品方向分别显示；轮换行不会重新混入总百分比。
- 同版本同种子同操作复现，保存／刷新／继续后的未来一致；读取快报与出售不消耗经济随机流。
- v3 原文完整校验、确认／取消、备份碰撞、写入失败、损坏 v4 隔离、迁入后的普通事件与结算、迁移链均有夹具。
- v2 已有保护和退出持仓继续覆盖，不通过放宽精确键、删字段或改现金迁就新版本。
- 浏览器中重大提示只在成功推进后出现一次；加载和导入不重播；静音和减少动效生效。

### 17.2 诊断步骤与指标

1. **小样本先查机制。** 沿用六个策略、三个难度，每组 30 个主种子，至少 540 局；另外做不驱动策略决策的事件频率和冲击分布诊断。
2. **只用主样本调参。** 独立留出种子不得边看边调；候选目录和参数获批后再冻结。
3. **重新跑新规则正式样本。** 六策略 × 三难度 × 主种子 1000 = 18000 局，独立留出同样 18000，合计 36000。旧 0.4 报告不能证明新增黑天鹅已平衡。
4. 若新规则继续暴露低购房率、单商品唯一解或租仓阻塞，只提交单独调整建议，不能自动改房价、费用或仓储标价。

必须记录：

- 黑天鹅合格周数、条件触发率、每局次数、首次发生周、最长间隔、每种事件实际出现率、过滤原因。
- 主冲击商品首周实际涨跌分位、绝对变化达到 25% 的比例、各角色普通周／普通事件周／黑天鹅周分布。
- 价格边界裁剪率、黑天鹅首冲裁剪率和持续中枢护栏触发率；按商品、事件、难度分开。
- 六策略实际购房率及区间、购房周、期末资产、年内现金低谷、最大回撤、空间阻塞和仓储投入。
- 名表、藏品、手机等小体积高本金商品的正利润份额、负贡献和现有集中度预警。
- 决策策略只读 `Engine.visible()`；真实事件参数、冲击与内部日志只能在**事后诊断**中读取，不能让机器人提前知道抽奖结果。
- 同难度同种子的价格路径不会因为六个策略重复运行而变成六份独立样本；涨跌观测数量不乘策略数。

推荐体验诊断目标：平均约 3–5 个黑天鹅／局；至少 70% 的主冲击观测达到绝对 25% 的实际周变化。两者是待冻结的诊断目标，不是自动验收承诺。另建议将黑天鹅主冲击裁剪比例超过 20% 设为复核告警：先分析商品／事件集中情况和强度，不直接抬高价格上限。

这些阈值都需要主审确认。更多刺激不能以“随机策略几乎必胜”或“所有正常策略都更难买房”为代价；反之，模拟达到阈值也不能替代人工对趣味性的判断。

新证据候选路径：`docs/black-swan-evidence/<运行标识>/`、`docs/black-swan-c1-*.json`、`docs/black-swan-primary.json`、`docs/black-swan-holdout.json` 和单独摘要。保留原 `simulation/c1.cjs`、`docs/gameplay-v4-c1-r2.*`、现有主／留出报告及其哈希作为历史基线。

### 17.3 人工试玩

自动化不能证明“好玩”。至少人工走两类局：

- 小额分散持仓：确认快卖易懂、事件能影响决策，却不会强迫每周猜方向。
- 集中持仓：体验重大下跌、未上架回收、等待回归及买房时机，检查损失原因是否清楚。

另外观察：是否过度频繁打断；阅读快报是否有实际价值；大事件后是否存在止损／兑现／等待的真实选择；第一次看到回收折价是否能理解。音效只检查已有提示是否合适，不以本轮重做音乐。
